# 分组额度容量与消耗趋势设计

状态：一期已实现，2026-10-24。管理员点击「额度趋势」后才查询和计算，无独立功能开关。下文保留设计和边界，文末记录使用方式与实现验证；版本发布与生产部署分别验证。

## 1. 产品目标与入口

管理员打开一个分组后，能直接回答：

1. 从现在起的 1h、5h、24h、3d、7d、15d 内，预计累计可以消费多少美元额度？
2. 最近消耗在增加还是减少？按近期速度继续消费，会在哪些区间出现容量压力？
3. 结论覆盖了多少账号，哪些账号或数据问题使估算不完整？

一期入口放在 **分组管理 → 每行操作 →「额度趋势」**，打开 `BaseDialog width="full"` 的独立监控面板。返回时保留分组列表的筛选、排序和位置。暂不增加一级导航，也不为所有分组默认计算 15 天预测。

功能命名用「额度趋势」或「额度容量」，避免和现有“容量”列的并发、会话、RPM 混淆。分组里的今日/昨日/累计费用继续保持现有含义。

首期模型仅支持 **OpenAI OAuth、global 文本额度、标准 5h/7d 双窗口**。其他平台、Spark、Web 图片、视频等不混进这个美元模型；详情中明确显示不支持或无法分类的部分。复合分组只展示符合该范围的 OpenAI 子集，不能标作复合分组总容量。

## 2. 管理员看到什么

面板顺序固定，最先看结论，再看依据，最后排查账号。

```text
UPI PLUS / 分组 24                         刷新统计  关闭
OpenAI global 文本 · 账号费用等效美元（预估） · 统计更新于 xx:xx
模型覆盖 x / 符合平台与额度范围 y；分组共 n；当前可调度 z
上游快照新鲜度 / 窗口来源完整性

[未来5h累计可用] [未来24h累计供需差] [近24h美元/小时]
压力提示：所选范围内何时首次出现模型累计缺口 / 数据不足

消耗依据：近24h / 近7d / 前24h        图上范围：24h / 7d / 15d
┌ 未来累计可用额度 —— / 累计消耗外推 - - - ┐
│ 悬停或触摸：区间终点、容量、外推消耗、差额、估算来源 │
└─────────────────────────────────┘

未来区间表：1h / 5h / 24h / 3d / 7d / 15d
范围 | 累计可用额度预估 | 累计消耗外推 | 累计供需差 | 数据覆盖/提示

当前账号池 global 文本实际消耗（24h / 7d / 15d，完整小时均速）
┌ 每小时账号池消耗 / 本分组调用消耗 ┐
└─────────────────────────┘
完整24h总额、与前24h变化、完整小时峰值

估算覆盖与账号明细（折叠）：缺窗口 / 旧采样 / 补估 / 暂停 / 共享
```

三个摘要值足够；不把“容量覆盖倍数”作为主要结论，以免部分账号覆盖时看起来像有确定余量。

金额旁提供说明：“按 Sub2API 账号费用折算，不是官方美元余额”。覆盖分母不能把不支持平台、状态排除和缺窗口混成一个百分比；分别列出分组总数、范围内账号、可调度账号、纳入模型账号以及历史消耗覆盖账号数。

### 2.1 未来容量图与时段表

- 容量表示 **从统计快照起，到所选终点之前的累计可消费额度**，包含期间重置后的再次使用。5h 的意思是未来 5h 内能用多少。
- 同图同轴展示累计容量和累计消耗外推，单位都是 USD。容量为阶梯线，消耗外推为虚线。
- 历史每小时费用是 USD/h 桶值，放在另一张图，避免与累计 USD 混用或使用双 Y 轴。
- 默认查看未来 15 天，默认以最近 24 个完整小时的账号池消耗均速外推。另可选近 7 天、前 24 小时；选择改变时不请求上游账号。
- 表格始终保留所有未来区间；「图上范围」仅缩放主图。点击一行可定位主图；5h、24h 等表格值由后端按准确事件边界计算。
- 悬停详情显示绝对时间、未来时长、累计容量、累计消耗外推、累计差额、直接估值/样本补估贡献和覆盖账号数。触摸固定详情，键盘也能选择时间。
- 正差叫「累计供需差」，不能叫「未来余额」「安全余量」或「保证充足」。首次负差叫「首次模型累计缺口」，不能叫「确定耗尽时间」。

### 2.2 历史与共享账号

默认按 **当前账号池** 判断容量压力：冻结查询时刻的成员集合，在符合本模型平台与额度维度的子集中，回看这些账号在所有分组的同维度消耗。这也包括其他分组对共享账号的使用。其他平台或额度维度不能混进默认需求均速。

历史图还显示 **本分组调用**：按请求记录 `group_id` 统计，包括后来移出本组的账号。两条曲线的成员范围不同，不能相加；本分组曲线是流量归属参考，不直接替换池口径作为“全池是否够用”的默认需求。

当前未结束小时独立标记；不参与完整 24h 环比、完整小时均速和峰值。用户可查看它的实际已记账金额，不能按比例冒充整小时实际值。

共享来源明细列出账号池在哪些分组消耗了多少。不再从供给曲线重复扣一次其他分组的消耗，因为需求均速已经包含它。跨分组总览也不能把共享池容量直接求和。

### 2.3 结论与数据状态

| 状态 | 管理员文案与行为 |
| --- | --- |
| 消耗外推超过模型容量 | “已估容量承压”，显示首次累计缺口时间；覆盖不完整时同时显示覆盖提示 |
| 全区间未见累计缺口 | “所选场景未见累计缺口”，不承诺调度成功或全组充足 |
| 窗口/金额估算覆盖不完整 | 显示“覆盖不完整 x/y”，正差仍不能显示全组充足 |
| 只有少量或没有历史请求 | 显示已有消耗；未来需求显示“历史不足/近期无记账消耗”，不显示无限覆盖 |
| 查询失败或快照超时 | 保留上次成功结果，标“已过期”及时间；不把失败置零 |
| 不支持的额度维度/平台 | 显示“不支持此美元容量模型”，允许查看可准确归类的历史消耗 |

“页面统计更新于”和“上游快照事件时间”是不同时间。面板顶端必须同时给出统计时间、快照新鲜度与窗口来源完整性摘要，详细时间分布放在折叠区。旧窗口字段不能因 GET 刚返回或其他窗口字段更新就变成“新鲜”。

## 3. 金额、时间与预测口径

### 3.1 账号费用统一口径

沿用账号窗口统计的费用：

```sql
SUM(COALESCE(account_stats_cost, total_cost)
    * COALESCE(account_rate_multiplier, 1))
```

它是面板的 **账号费用等效美元**，不是上游充值余额，也不是用户扣费 `actual_cost`。不使用分组日费用摘要或 Dashboard 的 `SUM(total_cost)` 替代。

按用量百分比推算满窗口金额只是一种估值：`窗口费用 / (已用百分比 / 100)`。模型、上下文、缓存、计价策略变化都可能影响估值；不能把百分比当成固定美元兑换率。

### 3.2 采样对齐

读取 `extra.codex_usage_updated_at`、原始 5h/7d 百分比、窗口长度和 reset。不要使用返回 DTO 的 `UpdatedAt` 作为上游采样时间，也不要使用展示层已把过期百分比清零的值。

**现有数据的重要限制：** `codex_usage_updated_at` 是最近一次快照事件的时间，不证明两个窗口每个字段来自同一次采样。写入方法无条件更新总时间，但窗口字段有值才更新，可能产生“新 5h + 旧 7d + 新总时间”。一期纯读模式不能恢复丢失的字段来源时间。没有窗口同批采样证据时，必须返回 `window_provenance=unverified`，降级为近似估值；不能宣称已经完成精确采样对齐或给出“上游已确认容量”。

每个账号/窗口：

1. 校验原始窗口长度、百分比、reset、快照事件时间及每个字段的来源证据。
2. 只有存在可验证的同窗口采样边界时，才把对应费用作为时间对齐样本；其余只能作为明确标记的近似初始估值，或排除。
3. 采样之后的本站记账费用另行估算扣减；上游站外使用未知，不作“已经全部扣除”的承诺。
4. 上游响应头采样与本站请求完成/记账可能有时差。无法准确对齐时标为近似估值，不把 `created_at` 当请求开始时间。
5. 百分比为 0、有效用量过小、费用异常、窗口跨越或无采样时不直接相除；同套餐/额度维度/计价版本样本不足时返回未知。
6. 样本补估使用经校验样本的中位数；返回样本数、范围、来源及补估贡献。没有足够样本时不凭空补成满额。

新鲜度首版建议：15 分钟内为近期快照事件，15 分钟至 2 小时为旧事件，超过 2 小时为过期事件；没有字段来源时间的窗口，其新鲜度另标未知。阈值是展示/纳入策略配置，不是准确率证明。缺少可靠扣减链、同批证据或有效估值时，不计入可靠估值部分，可单独列为补估参考。

已过 reset 只意味着按规则可能重置，不证明账号此后没有使用。没有新采样时，补满只可作为明确标记的模型假设，不能算“上游已确认可用”。

### 3.3 双窗口模型

每个可估账号保存 5h、7d 两个预算。一次消费同时扣两个预算，实际可用取两者剩余值的较小值，不能相加。

- 保留已知未来 reset；未来无活动窗口只有实际开始消费后才启动。
- 仅在明确到期的临时暂停之后模型恢复；手动禁用、认证失败、未知暂停不自动修复或启用。
- 自动到期的账号在到期后不贡献容量。
- 同一物理额度维度只计一次。去重需要已验证的上游主体身份 + 额度维度，不能只按数据库行 ID 或 workspace ID 宣称完成物理去重。团队不同成员也不能只因 workspace 相同而合并。身份语义无法证实时返回 `identity_quality=unknown`，不计入可靠部分。母账号和不同配额维度的影子不能简单相加或简单合并；一期只纳入可准确识别的 global 文本实体，其余明确排除。
- 图中供给是“额度释放后及时使用”的容量场景，不是对真实请求速率、并发、成功率或收入的预测。

`C(T)` 为上述模型在 `[as_of, as_of + T)` 内累计可消费金额；`T=0` 单独展示即时可用估值。恰好终点才释放的额度不计入这一段区间。

`r` 为完整历史区间的账号池费用均速，`D(T)=r*T`，`gap(T)=C(T)-D(T)`。

后端逐个额度释放区间计算首次 `D(T)>C(T)` 的时点，不只比较 5h/24h 等表格终点，也不把最后一次正差当成前面一直够用。

这个比较用于 **累计压力筛查**。低负荷可能推迟窗口启动；账号选择、模型约束和共享调度也影响可服务性，所以不能从正差推出真实调度可满足全部需求。需要按需求分配的队列模拟或并发容量判断时，应作为另一项独立能力设计。

### 3.4 覆盖范围必须显式

至少返回：当前成员、符合平台/维度范围、当前可调度、可估算、直接估值、样本补估、过期采样、窗口同批性未知、身份去重未知、缺窗口、状态排除、共享账号数量。直接估值仍是费用/百分比推算，并非官方美元余额。

容量覆盖 x 个账号，而池历史覆盖 y 个账号时，负差只表示“历史池消耗外推高于已建模容量”；它可能同时包含未知容量、历史成员变化和负载变化。不能据此断言整个分组在该时刻确实耗尽。

OpenAI global 文本费用与图片/视频/Spark 消耗也必须对齐。可用 `account` 额度维度、模型/计费模式/图片视频字段识别的请求归入明确范围；旧数据无法识别时返回未知贡献，不硬算作文本费用，不通过新写网关埋点扩展首版范围。

## 4. 后端接口与执行方式

新增独立管理员接口，保留原有 `capacity-summary`、`usage-summary`、Dashboard 语义。

```text
GET /api/v1/admin/groups/:id/capacity-monitor?history=7d&horizon=15d
```

分组列表不请求统计；管理员点击入口后，详情接口按需返回同一 `as_of` 下的本地快照。支持范围、时间边界和覆盖质量随详情返回：

| 字段 | 含义 |
| --- | --- |
| `as_of / timezone / currency / fee_basis / model_version` | 快照身份与计算口径 |
| `scope / membership_as_of / membership_fingerprint` | 当前成员回看、额度维度与去重边界 |
| `inventory / quality` | 分层覆盖分母、快照事件时间分布、窗口同批性、身份去重质量、直接/补估/未知原因 |
| `history[]` | 桶起止、complete、pool_account_cost、group_route_cost、同池本组/其他组费用、请求数 |
| `demand_bases` | 近24h、近7d、前24h的金额、小时数、均速和可用性 |
| `capacity_points[]` | 累计容量、直接/补估贡献、覆盖账号数 |
| `scenarios` | 各均速下的表格里程碑、首个累计缺口、区间内最小累计差额 |
| `shared_usage[]` | 池历史中各分组的消耗归属 |
| `cache / limitations` | 统计生成时间、有效期、历史完整性、局限和未支持维度 |

未知金额或不可计算时间返回 `null` 和原因，不用 `0`、无穷大或预计时间代替。内部金额保留精度，响应最多 6 位小数、显示两位；禁止 NaN/Infinity。

前端可用后端返回的均速绘制线性消耗线和格式化悬停值；预算、重置、采样纳入、里程碑和状态判定只在后端实现。

### 4.1 只读，批量查询

**不调用 `GetUsageBatch` / `getOpenAIUsage` 来刷新监控。** 当前方法可能触发上游 probe、更新账号 `extra`，并按账号分别查询 5h/7d 费用。监控接口必须独立读取已有快照。

一次详情加载：

1. 使用数据库 `REPEATABLE READ READ ONLY` 事务固定 `as_of` 和当前成员，读取轻量账号投影；不加载 token、Cookie、API key。必要身份仅投影用于去重，并在服务端生成不回传前端的去重键。
2. 一批聚合获取各账号按自身窗口/采样边界的费用和采样后的本地消耗，避免 N+1。
3. 一批聚合获取当前池全部分组的有界小时历史和共享来源；另一次有界聚合统计历史 `group_id=:id`，避免两个不完全相同口径被同一个 JOIN 漏掉。
4. 将必要投影复制到内存后结束事务，执行纯模型计算和响应构建，不长时间持有数据库快照。

首次查询超时或行数预算超限要明确失败，不截断账号集合后继续给全组结论。不存在读权限时返回 403；分组不存在返回 404；非法时间范围返回 400。

### 4.2 刷新、缓存和显示粒度

- 一期默认人工“刷新统计”，只刷新本地统计快照，不主动测活或查询上游额度。
- 账号测活/上游额度刷新仍使用现有账号页面动作，必须由管理员明确执行；本功能不另造探测逻辑。
- 详情使用 60 秒缓存 + singleflight + ETag；缓存 key 包括分组、时间范围、成员/数据版本与模型版本。成员或关键账号状态变化需使缓存失效；无法即时失效时响应显示不超过 TTL 的陈旧边界。
- 控制缓存条目数和允许参数组合；旧条目清理，不能让任意查询参数增长内存。不要用毫秒级“当前时间”作为缓存 key。
- 如后续增加 60 秒自动刷新，默认关闭，面板关闭/页面不可见时停止；只读同一个缓存接口，不周期性 probe。
- 历史最多 15 天小时桶（最多 361 个，含当前部分小时）；返回 `history_completeness=known/partial/unknown`。只有明确的保留/清理任务水位等证据才认为区间完整；最早日志、空桶或清理任务记录不能排除手动删库。完整性未知时，零桶仅表示“未观察到记录”，不能假装已证实无消费或用于高确信度外推。
- 内部预测按准确事件计算；图最多约 5,000 点。长区间可用 5 分钟采样并明确标注图粒度；保留表格里程碑与首个压力节点，不能用下采样结果判定预警时间。
- 一期复用现有 `(account_id, created_at)`、`(group_id, created_at)` 索引。先验证实际查询计划，确有性能缺口再另行审批索引迁移。
- 验收目标：155 账号、15 天窗口下冷查询 p95 ≤ 5s、缓存 p95 ≤ 200ms，响应未压缩 ≤ 1MB。这是待验证目标，不是当前性能结论；大池超过预算时明确提示。

## 8. 一期实现与使用

管理员进入「分组管理」，点击目标分组的「额度趋势」，即可查看从现在到未来 15 天的美元累计容量预估及历史消耗趋势；悬停图表可查看具体时段，表格可对比 1h/5h/24h/3d/7d/15d。面板提供人工「刷新统计」，不自动轮询。关闭面板会取消请求，系统不安排后台预计算或定时刷新。

实现只使用独立的 `:id/capacity-monitor` 接口。统计为数据库只读快照，60 秒缓存、ETag、singleflight；每次至多读取 1,000 个成员，超出时明确返回查询预算错误，不截断为部分分组结果。

线上规模验证后，快照总预算为 20 秒，单条 SQL 限制为 8 秒，仍在前端 30 秒请求超时内。身份字段每账号只提取一次，只聚合本组需要的全站身份；历史查询分开读取当前池与仅路由的请求，避免重复记录和不必要的账号关联。此前冷查询 p95 ≤ 5s 仍是优化目标，不能据此强制给顺序执行的三项查询共用 5 秒；原单条 SQL 4.5 秒也缺乏线上负载波动余量。超时返回 `CAPACITY_MONITOR_TIMEOUT`，内部日志记录失败阶段与耗时。

一期特别保守处理：缺少可用身份、重复导入主体、过期采样、缺少标准双窗口、未知认证/临时暂停等不强行算作供给。直接估值仍标为近似，历史完整性维持 unknown；没有可估容量时显示未知，不显示满额或零。历史按明确 token 消耗筛选，并检查实际/请求/上游模型，避免图片、视频、Spark 以及伪装别名混入文本额度。

已验证的本地范围：模型单元测试、点击才查询的懒加载行为、HTTP 参数/缓存/ETag、API golden 合约、真实隔离 PostgreSQL 中的费用与池/路由范围、前端组件与分组入口测试、类型检查、生产构建。实际 Vue 组件还使用固定测试数据检查场景切换、表格定位、键盘操作、320px 布局以及刷新失败保留旧结果。测试数据不构成线上容量证明。
